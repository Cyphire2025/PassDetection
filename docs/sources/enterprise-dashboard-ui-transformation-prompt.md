ENTERPRISE-GRADE DASHBOARD UI, UX AND FRONTEND PERFORMANCE
TRANSFORMATION PROMPT

You are not acting as a basic frontend code generator.

You are acting as the Lead Product Designer, Principal Frontend Architect,
Staff UI Engineer, Design Systems Architect, Interaction Designer,
Accessibility Specialist, Frontend Performance Engineer and QA Lead of an
established enterprise software company.

Your responsibility is to completely transform the specified dashboard page
or feature into a polished, premium, highly usable and enterprise-grade user
experience.

The primary scope of this task is:

- user interface design;
- user experience;
- frontend architecture;
- visual hierarchy;
- interaction quality;
- component quality;
- frontend rendering performance;
- perceived speed;
- responsive behavior;
- accessibility;
- consistency with the wider product;
- maintainable reusable UI implementation.

The objective is not to alter what the selected feature does.

The objective is to redesign how the selected feature presents information,
guides the user, responds to interaction and performs in the browser.

Preserve all existing business logic, data meaning, permissions, backend
contracts and intentionally designed workflows unless a confirmed frontend
bug requires correction.

Do not remove functionality.

Do not simplify the selected feature into a visually attractive but less
capable page.

Do not replace useful information with decoration.

The final page should look and behave like software produced by a mature,
well-funded, established enterprise technology company.

It must no longer feel like:

- a basic MVP;
- an admin template;
- a collection of default inputs;
- repeated white cards;
- the same search bar and dropdown on every page;
- a plain heading followed by a generic table;
- a page assembled from unrelated components;
- an unfinished internal tool.

It should feel intentional, differentiated, premium and production-ready.

==================================================
CORE DESIGN OBJECTIVE
==================================================

Transform the selected page so that it feels:

- premium;
- modern;
- professional;
- trustworthy;
- visually balanced;
- operationally efficient;
- information-rich without feeling crowded;
- fast;
- responsive;
- calm;
- clear;
- accessible;
- consistent;
- enterprise-grade.

The user should immediately understand:

1. where they are;
2. what the page is for;
3. what currently needs attention;
4. what the primary action is;
5. what information matters most;
6. what they can do next.

Every visual element must have a purpose.

Avoid decoration that adds rendering cost or visual noise without improving
understanding.

==================================================
IMPORTANT PRESERVATION RULES
==================================================

Do not change the underlying business workflow.

Do not remove existing actions.

Do not change authorization or permissions.

Do not change backend behavior unless a small supporting frontend contract
change is strictly necessary and safe.

Do not rename important business terminology without a strong UX reason.

Do not change data meaning.

Do not create additional clicks merely to make the interface look cleaner.

Do not hide frequently used actions inside unnecessary menus.

Do not move critical information into hover-only interfaces.

Do not apply one generic layout to every page.

Do not copy the same page structure already used throughout the dashboard.

The selected page must receive a design suited to its own purpose and data.

==================================================
FIRST PHASE — PAGE AND USER-WORKFLOW AUDIT
==================================================

Before redesigning the UI, inspect the complete selected page.

Understand:

- the primary user;
- the page's main purpose;
- the most common task;
- the most frequent secondary tasks;
- the information users need immediately;
- information that is only occasionally needed;
- states requiring attention;
- bulk operations;
- search and filtering behavior;
- empty states;
- loading states;
- success states;
- error states;
- long-running operations;
- role and permission differences;
- page density;
- realistic data volume;
- mobile/tablet/desktop requirements;
- related pages and navigation context.

Identify the current UI weaknesses.

Review whether the page suffers from:

- weak hierarchy;
- excessive similarity to other pages;
- generic cards;
- default-looking inputs;
- plain browser-style dropdowns;
- repetitive search bars;
- large unused whitespace;
- visually flat sections;
- repeated bordered containers;
- too many identical white surfaces;
- unclear primary actions;
- disconnected controls;
- poor grouping;
- inconsistent spacing;
- weak typography;
- low-information headers;
- unclear status colors;
- excessive text labels;
- actions far away from related content;
- poor empty states;
- generic icons;
- unnecessary columns;
- poor responsive behavior;
- excessive scrolling;
- layout shifts;
- frontend lag;
- delayed click responses;
- unnecessary rerenders;
- oversized component trees.

Do not begin with random visual changes.

First identify the page's actual information architecture and operational
priority.

==================================================
PAGE-SPECIFIC VISUAL IDENTITY
==================================================

The complete dashboard should remain one coherent product, but each page
should not look like a duplicated template.

Create a page-specific visual identity based on its function.

Examples of differentiation may include:

- operational command centre;
- document workspace;
- assignment workspace;
- readiness dashboard;
- timeline;
- grouped planning board;
- analytics surface;
- communication centre;
- account-management workspace;
- processing queue;
- review and exception workspace.

Do not use these examples blindly.

Determine the correct page personality from the actual selected feature.

The page should remain recognizable as part of the Global Connect dashboard,
but its composition should reflect what users do there.

==================================================
BRAND AND COLOR SYSTEM
==================================================

Use the Global Connect visual identity as inspiration.

The dashboard should use a balanced system built around:

- deep navy;
- strong clear blue;
- lighter travel-inspired blue;
- restrained lime or yellow-green;
- white;
- cool neutral surfaces;
- subtle warm accents where suitable;
- semantic success, warning, attention and error colors.

Do not turn the entire page blue or green.

Do not use lime for every selected element.

Do not use blue outlines around every interactive component.

Do not rely only on pale grey and white.

Use color strategically to communicate:

- hierarchy;
- selection;
- priority;
- status;
- attention;
- progress;
- completion;
- interactivity.

Ensure accessible contrast.

Color should enrich the interface without overwhelming it.

==================================================
PAGE HEADER TRANSFORMATION
==================================================

Do not use only:

- a plain page title;
- one sentence beneath it;
- a generic button on the far right.

Create a useful and visually polished page-top experience.

The page header should provide relevant context such as:

- page identity;
- operational summary;
- active workspace or group;
- key status;
- primary action;
- important alerts;
- selected filters;
- recent activity;
- compact metrics;
- contextual navigation;
- date or scope information.

The exact structure must depend on the selected page.

Possible patterns include:

- compact command header;
- contextual workspace banner;
- split header with primary action;
- summary strip;
- progressive page title with live status;
- contextual breadcrumb and action rail;
- compact hero with useful metrics;
- page-specific navigation tabs.

Do not create an oversized marketing-style hero.

Do not waste vertical space.

The page header must improve utility, not merely appearance.

==================================================
INFORMATION ARCHITECTURE
==================================================

Reorganize the selected page around the user's actual task.

Establish clear layers:

1. page context;
2. critical summary;
3. primary controls;
4. working content;
5. exceptions or attention states;
6. supporting details;
7. secondary actions.

Group related information together.

Separate:

- configuration;
- current status;
- action controls;
- results;
- warnings;
- history.

Avoid placing all fields and controls inside one large undifferentiated card.

Avoid excessive nested cards.

Use sections, surfaces, dividers, spacing and typography deliberately.

Important information should be visually prominent.

Secondary information should remain available without competing for
attention.

==================================================
SEARCH EXPERIENCE
==================================================

Do not automatically use the same large generic search box used elsewhere.

Design search according to the selected page.

Possible improvements include:

- compact search integrated into the page toolbar;
- contextual search with a useful placeholder;
- searchable command palette;
- filters combined with search;
- search result count;
- recent searches;
- search shortcuts;
- clear reset action;
- deferred suggestions where useful;
- inline search inside the relevant section;
- collapsible advanced search.

The search placeholder must reflect what can actually be searched.

Avoid vague placeholders that list every possible field.

Search must:

- respond immediately;
- debounce expensive requests;
- cancel stale requests;
- preserve the latest result;
- clearly show active search state;
- allow easy clearing;
- work through keyboard interaction;
- preserve page performance on large datasets.

==================================================
FILTERS AND DROPDOWNS
==================================================

Replace default-looking selects and repetitive rectangular dropdowns where a
better interaction is appropriate.

Use modern enterprise components such as:

- searchable combobox;
- multi-select;
- filter chips;
- segmented control;
- command menu;
- grouped options;
- popover filter panel;
- compact status selector;
- date-range picker;
- saved filter view;
- contextual inline selector.

Do not replace every select merely for visual novelty.

Choose the interaction appropriate to:

- number of options;
- frequency of use;
- whether multiple values are allowed;
- whether search is needed;
- whether the choice changes the whole workspace;
- whether the option is an action or a filter.

Dropdowns and filters should support:

- keyboard use;
- clear selected state;
- accessible labels;
- search where beneficial;
- loading state;
- empty state;
- safe closing;
- no layout shift;
- responsive placement;
- obvious reset.

==================================================
CARDS AND CONTENT SURFACES
==================================================

Do not render every item as the same white rounded rectangle.

Create a deliberate surface system.

Possible surface types include:

- summary metric;
- actionable item;
- status panel;
- grouped section;
- detail panel;
- attention panel;
- timeline item;
- compact list row;
- table;
- operational card;
- progress card;
- empty state;
- drawer or side panel.

Use different visual treatments based on purpose.

Reduce unnecessary borders.

Use shadows sparingly.

Use spacing and background contrast instead of placing every section inside a
card.

Avoid excessive rounded corners.

Avoid making every element visually elevated.

Interactive cards must clearly appear interactive.

Static summary surfaces should not look like buttons.

==================================================
TABLE AND LIST DESIGN
==================================================

Where the selected page contains lists or tables, redesign them for clarity
and efficiency.

Determine whether the content is best represented as:

- table;
- compact list;
- grouped list;
- cards;
- master-detail layout;
- board;
- timeline;
- expandable sections;
- hybrid table/card layout.

Do not convert a table into cards without considering density.

Do not use cards for hundreds of records if a table is more efficient.

Improve:

- row hierarchy;
- column priority;
- status display;
- actions;
- selection;
- sorting;
- filtering;
- pagination;
- grouped data;
- empty rows;
- hover and focus states;
- sticky headers;
- responsive behavior;
- compact and comfortable density modes where useful.

Frequently used actions should be immediately accessible.

Secondary actions may use a contextual menu.

Avoid one large action button in every row when a compact action system is
more suitable.

==================================================
METRICS AND SUMMARIES
==================================================

Do not automatically show three identical metric cards at the top of every
page.

Use metrics only when they help the user decide or act.

When metrics are useful:

- prioritize meaningful values;
- include context;
- show trends or state where relevant;
- connect metrics to actions;
- visually distinguish attention states;
- avoid decorative totals that provide no decision value.

Metrics may be represented through:

- compact summary strip;
- inline counters;
- progress ring;
- status distribution;
- mini trend;
- grouped readiness indicators;
- attention badge;
- operational health summary.

Choose the representation appropriate to the page.

==================================================
EMPTY STATES
==================================================

Create thoughtful page-specific empty states.

An empty state should explain:

- what is absent;
- why it may be absent;
- what the user can do next;
- whether configuration is required;
- whether permission is missing;
- whether filters are hiding results.

Include a useful primary action when appropriate.

Avoid large empty bordered boxes containing only a generic icon.

Avoid generic copy such as:

- No data found;
- Nothing here;
- No records.

Use language specific to the selected feature.

Do not make empty states excessively decorative.

==================================================
LOADING EXPERIENCE
==================================================

The page should never feel frozen or unfinished.

Use:

- immediate page shell;
- cache-first rendering;
- progressive content;
- section-level skeletons;
- subtle inline loaders;
- optimistic interaction where safe;
- silent background refresh.

Avoid:

- blank pages;
- full-screen spinners;
- replacing loaded content with skeletons during refresh;
- flashing between states;
- repeated loading indicators;
- blocking the entire page for one secondary request;
- technical loading messages.

Loading design must match the final layout to avoid movement after content
appears.

==================================================
INTERACTION DESIGN
==================================================

Every click should provide immediate visual feedback.

Improve:

- button press states;
- row selection;
- hover feedback;
- keyboard focus;
- expandable content;
- dialog opening;
- drawers;
- confirmation;
- destructive actions;
- bulk actions;
- drag-and-drop where genuinely useful;
- inline editing where safe;
- undo where appropriate.

Do not add animation that delays the user's task.

Do not make users wait for the backend before acknowledging a safe action.

Do not use modal dialogs for every simple operation.

Use:

- modal when focus is required;
- drawer for contextual detail or editing;
- inline editing for small safe changes;
- dedicated workspace for complex tasks;
- confirmation only for meaningful risk.

==================================================
MOTION AND VISUAL POLISH
==================================================

Add restrained, professional motion.

Use subtle transitions for:

- opening panels;
- switching views;
- expanding sections;
- status changes;
- loading completion;
- row updates;
- success confirmation.

Animations must be:

- short;
- smooth;
- interruptible;
- GPU-friendly;
- non-blocking;
- accessible;
- disabled or reduced when the operating system requests reduced motion.

Avoid:

- bouncing;
- excessive scale animation;
- long fades;
- large blur filters;
- parallax;
- decorative continuous motion;
- expensive shadows or effects.

The page should feel refined, not theatrical.

==================================================
FRONTEND PERFORMANCE
==================================================

The redesigned page must not merely look premium.

It must also perform like premium software.

Audit:

- initial JavaScript cost;
- page bundle size;
- component mount time;
- render count;
- unnecessary rerenders;
- global state subscriptions;
- React Query subscriptions;
- unstable props;
- unstable callbacks;
- expensive derived state;
- filtering;
- sorting;
- grouping;
- list rendering;
- DOM size;
- image loading;
- icon loading;
- animation cost;
- layout recalculation;
- event listeners;
- timers;
- browser storage access.

Optimize where evidence supports:

- route-level code splitting;
- lazy loading;
- focused state selectors;
- normalized data;
- memoized derived values;
- stable references;
- list virtualization;
- server-side pagination;
- incremental rendering;
- request cancellation;
- deferred non-critical rendering;
- prefetching likely next interactions;
- batched state updates;
- CSS containment where beneficial;
- efficient icon imports;
- responsive image sizing.

Do not add memoization blindly.

Do not create stale state or complexity for meaningless micro-optimizations.

Only the components affected by a change should rerender wherever practical.

==================================================
PERCEIVED PERFORMANCE
==================================================

Design for both actual speed and perceived speed.

Target behavior:

- click feedback within approximately 50–100 ms;
- previously loaded panels and dialogs opening immediately;
- cached page content appearing without visible delay;
- search input never lagging behind typing;
- local filter changes appearing immediately;
- layout remaining stable;
- background refresh remaining invisible;
- common transitions feeling continuous.

Do not fake completion.

Long operations must show truthful progress.

==================================================
RESPONSIVE DESIGN
==================================================

Transform the page for realistic desktop sizes and narrower screens.

The dashboard should work at:

- large desktop;
- standard laptop;
- smaller laptop;
- tablet where currently supported;
- browser zoom;
- increased text size.

Avoid fixed widths that cause:

- horizontal clipping;
- broken tables;
- hidden actions;
- overlapping controls;
- excessive empty space.

Use responsive composition rather than merely shrinking the desktop layout.

Prioritize important content as space becomes limited.

Secondary controls may move into contextual menus or drawers.

==================================================
TYPOGRAPHY
==================================================

Create a deliberate typography hierarchy.

Define consistent use of:

- page title;
- section heading;
- card heading;
- body;
- metadata;
- caption;
- status;
- button label;
- table header;
- numeric metric.

Avoid excessive font weights.

Avoid making every heading bold.

Use typography to guide attention.

Line height, width and spacing should improve readability.

==================================================
ICONOGRAPHY
==================================================

Use one coherent icon system.

Icons should:

- have consistent stroke weight;
- use consistent sizing;
- align correctly with labels;
- communicate meaning;
- not replace necessary text;
- support accessible labels where icon-only;
- avoid decorative repetition.

Do not place icons inside identical blue boxes everywhere.

Use icon containers only where they improve hierarchy or recognition.

==================================================
FORMS
==================================================

Transform forms from default MVP styling into polished enterprise forms.

Improve:

- grouping;
- labels;
- helper text;
- validation;
- field width;
- dependent fields;
- required indicators;
- autocomplete;
- searchable selection;
- inline errors;
- success states;
- keyboard navigation;
- save behavior;
- cancellation;
- unsaved-change protection.

Avoid one large vertical stack of full-width inputs where a structured layout
is more usable.

Do not use placeholders as replacements for labels.

Destructive actions must be visually distinct and carefully confirmed.

==================================================
DIALOGS, DRAWERS AND OVERLAYS
==================================================

Redesign overlays according to task complexity.

Dialogs should have:

- clear title;
- concise context;
- organized content;
- one clear primary action;
- restrained secondary actions;
- loading and error behavior;
- keyboard support;
- focus trapping;
- escape behavior where safe.

Use drawers or side panels for:

- inspecting records;
- editing contextual information;
- preserving the user's current page position.

Do not open small generic modal boxes for complex multi-step work.

Do not use full-page navigation for tiny actions.

==================================================
STATUS AND FEEDBACK
==================================================

Create a semantic and consistent status system.

Represent statuses using appropriate combinations of:

- text;
- icon;
- color;
- shape;
- progress;
- tooltip;
- explanation.

Do not depend on color alone.

Avoid dozens of unrelated badge styles.

Success, warning, pending, active, disabled, blocked and failed states must be
clearly distinguishable.

After actions, show useful confirmation without interrupting continued work.

==================================================
ACCESSIBILITY
==================================================

The transformed page must support:

- keyboard navigation;
- visible focus;
- correct semantic HTML;
- screen readers;
- descriptive labels;
- correct dialog behavior;
- proper heading order;
- sufficient contrast;
- non-color state communication;
- text scaling;
- zoom;
- reduced motion;
- appropriate target sizes;
- accessible tables;
- error announcements;
- logical tab order.

Do not trade accessibility for visual minimalism.

==================================================
DESIGN SYSTEM AND REUSABILITY
==================================================

Use or improve the existing shared design system.

Create reusable primitives only when they have genuine reuse value.

Potential shared elements may include:

- page context header;
- contextual toolbar;
- premium search component;
- filter system;
- metric presentation;
- status badge;
- list row;
- table action menu;
- empty state;
- loading state;
- detail drawer;
- confirmation dialog;
- section header;
- responsive grid;
- command menu.

Do not create page-specific copies of components that already exist.

Do not force every page to use the same components in the same arrangement.

The design system should create consistency while still allowing pages to
have different information architecture.

==================================================
CODE QUALITY
==================================================

The frontend implementation must be:

- strongly typed;
- modular;
- readable;
- testable;
- reusable;
- maintainable;
- accessible;
- responsive;
- performant.

Reduce:

- duplicated JSX;
- duplicated styling;
- duplicated page shells;
- inline magic values;
- inconsistent spacing;
- one-off status implementations;
- large monolithic components;
- tightly coupled data and presentation logic.

Separate:

- business data;
- view state;
- layout;
- presentation;
- interaction logic;
- reusable components.

Do not overengineer simple interactions.

==================================================
ERROR STATES
==================================================

Create polished page-specific error behavior.

Distinguish:

- initial page failure;
- secondary panel failure;
- failed mutation;
- stale data;
- permission issue;
- empty search;
- network interruption;
- server failure.

Do not replace the entire page with a generic error when only one section
failed.

Preserve usable cached content.

Provide a clear retry or recovery action.

Never expose raw backend errors or technical stack information.

==================================================
BEFORE-AND-AFTER FRONTEND MEASUREMENTS
==================================================

Where practical, measure:

- page bundle size;
- initial render time;
- cached reopen time;
- click-to-panel latency;
- search response time;
- component render count;
- rows rerendered after one change;

Do not fabricate results.

Explain whether each result was measured locally, synthetically or in a
browser profile.

==================================================
VISUAL REVIEW REQUIREMENT
==================================================

After implementation, inspect the rendered page at multiple viewport sizes.

Check:

- visual hierarchy;
- spacing;
- alignment;
- color balance;
- density;
- empty states;
- populated states;
- long names;
- large counts;
- overflow;
- keyboard focus;
- zoom;
- responsive behavior.

Do not consider the work complete only because the code compiles.

The final rendered page must be visually reviewed and refined.

==================================================
FINAL ACCEPTANCE CRITERIA
==================================================

The transformation is complete only when:

- the page no longer feels like a default admin template;
- it no longer copies the same generic structure used across other pages;
- its layout reflects its actual purpose;
- the primary action is obvious;
- important status and attention items are immediately understandable;
- search and filters feel integrated rather than added afterward;
- dropdowns and forms feel modern and professional;
- cards and surfaces are not repetitive;
- empty states are useful and page-specific;
- loading is progressive and non-blocking;
- interaction feedback is immediate;
- the page remains smooth with realistic data;
- unnecessary rerenders are removed;
- the page is responsive;
- accessibility is preserved;
- color usage is balanced and brand-aligned;
- the UI feels premium and established;
- all existing workflows remain functional;
- tests, lint, type-check and production build pass.

The user should look at the page and think:

“This feels like a serious established company's enterprise product.”

They should not think:

“This is a basic dashboard template with different data.”
