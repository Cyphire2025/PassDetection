# MCP staged travel-document PDF ingestion — local qualification

This first business-ingestion lane takes one already staged PDF and appends it to the existing travel-document distribution workflow as a retained **draft**. Classification and passenger matching are bounded synchronous work. It does not claim to be a background OCR job, does not require broker publication, and does not implement passport image replacement/import or arbitrary file ingestion.

## Tool and recovery contract

- `inspect_document_pdf_ingestion` requires the opaque upload artifact, explicit agency/group, and one existing document lane (`visa`, four flight-ticket lanes, or `other`). It returns a revision covering source hash/size, group association, canonical passenger matching fields, and linked matching evidence. It does not parse or create a batch.
- `ingest_document_pdf` requires the same input, inspected revision, and stable idempotency key. A database-only operation first claims the artifact and commits a queued immutable receipt containing its internal UUID rather than the raw handle. A separate execution reads and verifies the exact bytes, rescans them through the existing security service, and runs the canonical isolated classifier/matcher.
- `resume_document_pdf_ingestion` explicitly resumes the saved operation ID. Current capability, identity, agency/group policy, and every artifact association are revalidated. A newly authorized connection for the same actor may explicitly acquire a protected source-access record. Automatic execution remains bound to the original operation and upload grant. An expired queued source cannot run.

One artifact can be claimed by one ingestion operation; another retry key cannot append it twice. Identical-key retry replays the original queued receipt and observes the same retained result. The operation UUID is the draft batch UUID. Existing `DocumentUploadChunkModel` records the single physical file, accepted/rejected count, byte count, SHA-256 and rejected-document details. Metadata says queued/ingested only when the corresponding operation/batch exists. Successful retained business drafts can be observed after temporary source expiry; a missing retained batch or association is never recreated.

No replacement callback, forced passenger match, manual document-type override, draft save, autoapproval, outgoing message, or provider OCR is exposed. Unmatched documents remain reviewable rejections. Source files and staged originals are preserved. Files copied successfully into the business workflow use the canonical fresh UUID namespace and remain governed by the existing document lifecycle.

## Transaction, resource and cleanup boundaries

Migration `0118_mcp_pdf_ingestion` adds nullable unique `mcp_artifacts.ingestion_operation_id`, referencing the durable operation with `ON DELETE RESTRICT`. The claim commits before parsing or object writes. A process loss at that boundary leaves an explicit resumable operation; there is no untracked broker enqueue gap.

At execution start, authority and operation/source are read under locks, then plain bounded inputs are captured and those locks are released. The entire source stream must match the recorded size/hash, current upload bound, source/token expiry and 120-second stream deadline. Malware evidence records the second scan under `mcp_document_pdf_ingestion`.

Before the canonical service persists its new draft, the adapter reacquires current authority, operation/source, group, linked matching records and passport rows. It compares the original revision again. Group/passport and batch row locks use `NOWAIT`; PostgreSQL canonical source locks use a local 250ms lock timeout. Existing advisory upload-scope locking, incomplete-upload exclusion, and assignment-capacity checks remain in force. There are at most two ingestions per backend process; matching reads cap both passports and linked source evidence at 5,000 rows. Exceeding a cap fails instead of truncating the roster. The shared source reader has an optional bound; existing web callers retain their prior default.

The canonical storage compensation removes only new keys claimed by a failed attempt. It retains durable cleanup jobs on cleanup failure using existing machinery. Cancellation drains the in-flight canonical operation before rolling back and compensating, preventing a worker from writing after cleanup. A concurrent winner causes the losing attempt to remove its new private copy and return the winner's draft. Failure after canonical SQL flush also rolls back the draft and receipt. An ambiguous final commit never triggers destructive compensation because the business transaction may already be durable.

## Evidence and remaining gates

- `backend/tests/integration/test_mcp_pdf_ingestion.py`: 13 tests using real PDF generation, actual security/parser validation and canonical classification/matching with synthetic scanner/object-store adapters. Covers draft and scan evidence, immutable receipt replay, distinct-key claim rejection, explicit new-grant recovery, capability removal, checksum/scan/storage failures, roster changes after storage, unmatched rejection, source expiry, missing retained result, DB-only preparation, cancellation drainage, and failure after canonical persistence.
- `backend/tests/service_integration/test_mcp_pdf_ingestion_postgresql.py`: 4 tests passed against the disposable loopback PostgreSQL database after migration 0118. Independent connections converge on one draft; grant revocation and passport correction during private copy prevent persistence; a revoked original connection requires explicit new-grant recovery. The concurrency test staggers classification before overlapping storage because the production parser correctly rejects simultaneous saturated admission.
- Shared website matching/staging and canonical ingestion tests passed with the extraction. Dedicated source-bound tests assert SQL bounds, reject oversized snapshots, and preserve the default web contract.
- `mcp-connector/tests/test_pdf_ingestion_tcp.py`: 1 test passed through official SDK client → local connector proxy → real loopback TCP backend, including explicit local-file staging, inspection, ingestion, identical-key retry, explicit resume, one draft/assignment, two scans and unchanged local/staged originals.
- Scoped Ruff and mypy passed for the seven touched production modules. No dependency changes were needed.

The storage and malware provider adapters in these tests are synthetic. Real production S3/ClamAV availability, lifecycle/cleanup operations, workload capacity, browser MFA/vault access, and real Codex file-authority handoff remain separate qualification gates. Other upload families and the full Phase 4 release are not qualified by this lane.
