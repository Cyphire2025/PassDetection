Scope and limits
- Unit totals above are distinct: 123 Vitest tests across 21 files, plus 29 Node
  tests. They are selected feature and regression coverage, not the entire repo.
- Browser flows use isolated synthetic API responses and document bytes. No
  real WhatsApp OTP, production storage, agency data or delivery service is used.
- Company and returning UI flows exercise widths 320 and 1440 pixels; large
  WhatsApp imports exercise 390 pixels. Company matching uses one 25-case page,
  explicit person selection, evidence acknowledgement and both case/group
  revisions. A resolved association is described as pending roster membership,
  never as consent, completed collection or an automatic profile merge.
- The large-import fixture has 700 traveller source rows: one delivery contact
  and 699 duplicate-phone rows; the preview contains only 500 duplicate rows.
  Both create/add browser flows verify original-file multipart submission,
  preserved edited delivery JSON and the full pending count of 700. Fixture
  bytes test transport, not workbook parsing; the backend workbook parsing and
  deduplication tests are separate evidence owned by the backend implementer.
- At most 10 original workbook File references are retained in the open dialog;
  the server enforces a combined 2,000-entry source budget. A truncated preview
  lacking an authoritative all-duplicate summary fails before mutating draft
  contacts. Original sources recover records only, never silently recreate
  removed delivery recipients.
- Returning state and replacement intent remain in memory. Lazy authorised
  document blobs are revoked on close; image pixel-memory capacity has not been
  measured. Per-trip passport selection and stale review refresh reset explicit
  image/field confirmation before completion.
- Wall times are test-run durations, not latency SLOs or capacity measurements.
  These checks do not establish throughput at millions of users, production
  latency percentiles, memory under sustained concurrency or real queue depth.
