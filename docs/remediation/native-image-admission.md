# Native image memory admission — 27 September 2026

This is a separately discovered **High availability defect**, found during the remediation's actual memory qualification. It is not an additional closure counted against an original audit ID. Four API worker processes could previously decode/transform maximum accepted images simultaneously: the measured worst crop used about 1,202.5 MiB in the isolated probe, while the original API container budget was 3 GiB. The final qualified KVM4 profile uses a 2,560 MiB API cap. A per-process semaphore cannot enforce the container's memory budget.

`app/core/native_image_admission.py` now admits one complete native pixel lifetime per container across processes and threads. Four kernel-backed tickets bound admitted work to one executing operation plus three waiting operations; admission waits at most five seconds, before any image decoding. Linux uses `flock`; the Windows development implementation uses byte-range locks. Worker death closes the descriptor and releases admission without a lease expiry or an overlapping replacement decoder. Files are never unlinked while the service is running. Unsafe ownership, permissions, symlinks and lock failures fail closed. Reentrancy belongs to the exact process and native thread, not to a copied asynchronous context. An awaiting task's cancellation therefore cannot release a decoder that is still executing. Forked parser children close inherited admission descriptors.

The shared boundary covers upload validation, image inspection, saved crops, thumbnails, Visa-photo canonicalization and ECR preparation. All production asynchronous callsites reviewed dispatch these synchronous operations through `asyncio.to_thread`; there is no five-second lock wait on the API event loop. ECR retains its existing two preparation slots **before** shared admission, with one combined five-second waiting deadline. This matters because its eight provider lanes must be able to finish preparation without the fifth lane repeatedly cancelling the drain. Decoding is serialized; provider requests retain their existing concurrency and quota policy.

Repeated requests exposed a second necessary part of admission: closing Pillow images does not guarantee that the native allocator returns unused pages to the operating system. The first four-process API image actually OOM-killed workers after their retained heaps accumulated. The qualified Linux GNU runtime now calls `malloc_trim(0)` after all pixel buffers close, while the shared execution lock is still held. An unsupported Linux allocator fails closed before decoding. Windows retains its separately tested lock behavior; Linux-only heap qualification is not attributed to Windows.

HTTP overload returns a structured `IMAGE_PROCESSING_BUSY` error with status 503, `Retry-After: 5`, and `Cache-Control: no-store`. It does not change accepted formats, dimensions, pixel limits, crop rotations, sharpening controls or persisted image bytes. The public upload controller displays the server's message, retains its idempotency credential, and retries only after an explicit action.

ECR capacity pressure propagates as a retryable dependency failure instead of becoming `invalid_image` or a terminal item result. Interrupted document batches retain completed results and requeue unsettled work. Passport ECR rows refund work attempts that never reached the provider; repeated admission failures leave them queued. Visa jobs likewise retain the accepted durable row, clear dispatch state and refund capacity-only job attempts; a later capacity notification cannot reset a completed row. Existing Celery retry/status-poll dispatch mechanisms remain in use. Provider billing or delivery semantics are not claimed to be exactly once.

The buffer-lifetime optimization is a separate change qualified by the reliability lane: 453 tests plus three subtests preserved encoded-byte equivalence across formats, EXIF orientations, rotations and both sharpening versions. Its source-overlay measurements reduced the worst crop to about 705.4 MiB, RGBA upload validation to 517.2 MiB, Visa canonicalization to 315.1 MiB and a single ECR preparation to 485.8 MiB. Those are isolated diagnostic measurements; final-image load and memory qualification must use the newly built artifact before deployment is claimed.

The final rebuilt image `0066ad357a08c4b207fa93bfa12e6111a90ebcac3514b4edbbdeb31a66db0f67` passed the actual four-Gunicorn-worker HTTP crop probe with no source overlay. Three rounds at concurrency 4, 8 and 8 used real 24 MP images padded to 10 MiB, 45-degree rotation and maximum version 2 sharpening. Six initial requests completed and 14 returned the documented capacity 503; all 14 explicit retries completed. All 20 logical requests produced the same deterministic output hash. The same four worker PIDs survived; cgroup peak was **2300.18 MiB under 2,560 MiB**, with zero memory-limit, OOM or OOM-kill events, including the final cgroup read before stopping. The host kernel OOM-kill counter stayed 6 throughout. The probe exited normally and Docker reported no OOM kill. This proves the native memory boundary in the isolated imported application, not warmed database/full-stack throughput. See [api-native-memory-evidence.json](api-native-memory-evidence.json).

A preceding attempt with the same final image was killed during overlapping qualification workloads on the 7.36 GiB local Docker host. Its last successful sampled peak was below the container cap, but the earlier harness did not retain terminal cgroup counters, so its kill cause remains **unclassified**. That failed attempt is preserved in [api-native-memory-interference-evidence.json](api-native-memory-interference-evidence.json). The final passing run used an explicitly quiet window after other heavy processes and temporary service fixtures stopped; it does not erase the failed attempt or prove a whole-host workload budget.

Evidence and source digests are recorded in [native-image-admission-evidence.json](native-image-admission-evidence.json). The Linux checks exercise actual process locks, forced holder death, parser-fork descriptor release, same-thread nesting, thread contention, cancellation, all six real entry points before Pillow decoding, eight concurrent ECR preparations, durable ECR/Visa recovery, and the HTTP error contract. The frontend test exercises the actual upload controller's visible error and explicit retry. They supplement the earlier full-suite evidence; they are not represented as a new clean run of the entire repository. Verbose intermediate logs remain local and are excluded from Git.

No production container, volume, image data, native application or live provider setting was changed by this implementation lane. The original physical-device and assistive-technology acceptance limitations remain separate.
