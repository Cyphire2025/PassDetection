# Existing VPS memory capacity: release constraint

Dated27September2026. These are sanitized numbers reported by the coordinating workstream's actual read-only VPS inspection. No production limits, services, data or host memory settings were changed.

The host reports15,992MiB physical RAM (15.617GiB),9,312MiB currently available and no swap. Twenty running container limits total23.375GiB. Selected caps are backend3GiB, frontend768MiB, extraction2GiB, MyPhotos1.5GiB, most other workers1GiB each, ClamAV4GiB and PostgreSQL2GiB. This is existing oversubscription, not additional memory already consumed or newly introduced by this patch. Idle usage does not qualify simultaneous peaks.

With the existing conservative2GiB host reserve, allowed total bounded container ceilings would be13.617GiB. Current23.375GiB exceeds that by9.758GiB. `verify_deployment_resource_budget.py` must reject this envelope. The current guide requires an exact private production render, including protected overrides, and stops on failure. Passing local API load under a3GiB API cap does not establish that all services fit the real host concurrently.

The generic checker includes every rendered profile service. Maintenance-only database admin/migrate services add512MiB each, although the supported release invokes them serially. Copy/staging and normal application phases need distinct honest envelopes; the release already stops application writers during storage migration. Correct phase accounting can avoid counting mutually exclusive tasks together, but cannot explain away23.375GiB of already-running service limits. PostgreSQL, Redis, ClamAV and retained old storage remain memory consumers during maintenance. No exact maintenance-phase pass is claimed without the real rendered inputs and measured transient tasks.

A no-additional-host-cost path requires a reviewed smaller deployment profile: measure bounded representative maximum-size PDF/image/OCR/MyPhotos/email tasks, simultaneous workers, ClamAV reload and Redis persistence/fork pressure; then qualify explicit child counts/caps and a combined peak/overload/recovery run inside the physical reserve. A lower cap is a real behavior change that can cause OOM/retries, not a formatting correction. Preserve accepted job state and verify recovery. Queue consolidation or mutually exclusive worker scheduling also changes latency and isolation and requires its own review and tests. No arbitrary cap reductions, swap assumption, disabled scanner, stopped business consumer or broadened budget exception is proposed as a shortcut.

The existing running VPS should remain intact until this capacity requirement and the separate signed-artifact/data-preserving migration requirements are satisfied. This assessment does not require buying another plan; it refuses to claim the present unqualified envelope is safe. Actual physical-host HA, full provider workload and sustained production capacity remain unproved.
