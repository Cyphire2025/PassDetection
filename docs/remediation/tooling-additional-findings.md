# Additional tooling and runtime defects found during remediation

Reviewed 27 September 2026. These five groups are separate from the original finding register; they do not alter its denominator. Severity describes the release or security-control consequence. A package scanner match is not evidence of an exploitable application path.

| ID | Priority | Origin | Concrete failure | Fix and observed status |
| --- | --- | --- | --- | --- |
| NEW-TOOL-01 | High | Pre-existing dependency-inventory gap; discovered while extending the original package-only audit | Runtime images contained vulnerable OS packages, native libraries and installer dependencies that the Python/npm application lock audits did not inventory. The initial backend image had 134 High/Critical package matches across 88 IDs; the old frontend runtime had 31 matches across 22 IDs. Those are inventory counts, not independent exploit counts. | Full-image SBOM and scanner gates now run on the actual candidate images. Unused runtime installers and video/URL/archive features were removed; maintained Node/OpenSSL and content-pinned parser builds were qualified. Backend policy currently passes with 56 scanner matches across 19 IDs individually investigated; five IDs remain **mitigated, not patched**, with executable deployment checks and a 30-day expiry. Frontend runtime candidate has zero High/Critical matches and two Medium matches for one BusyBox advisory. Final application-image rebuilding/scanning and actual signed CI promotion remain required. |
| NEW-TOOL-02 | High | Pre-existing embedded-parser exposure; the first remediation attempt was incomplete | Upgrading the OS Expat package did not repair Python's separately embedded pyexpat parser. A malformed UTF-16 input was still accepted by the original CPython extension. Treating the OS package version as proof would have falsely closed the parser exposure. | `backend/docker/build_xml_security.py` verifies official Debian package/source hashes and rebuilds the unchanged CPython extension against the patched Expat ABI. Actual negative XML probes, XLSX round-trip and 136 spreadsheet regressions passed. This is a distinct linkage-verification defect within the inventory work; its advisory IDs are not counted again as separate findings. No application exploitability was asserted from that input alone. |
| NEW-TOOL-03 | High | Introduced in the first version of the new advisory-disposition guard; caught before release | The first deployment guard checked UID/capabilities and bind mounts but could accept named-volume/code overlays, interpreter/loader overrides, custom confinement profiles or alternate startup commands. A scan of one image could then be used to justify different runtime code or call paths. The original Perl absence test also accepted a generic missing-dependency error for an installed target module. | `scripts/image_runtime_policy.py` now rejects unreviewed overlays, loader/interpreter settings, custom security profiles, entrypoints, commands, host devices and privilege additions. The storage copier has an exact separately confined contract. The probe requires the exact missing target Perl module diagnostic. Ten policy test cases include hundreds of concrete negative mutations; production Compose validation and 114 release-helper tests pass. The actual backend native/parser probe passes after the refinements. Local closure; future changes must retain the same enforced boundaries. |
| NEW-TOOL-04 | High | Introduced in the new signed-artifact flow; caught before release | Advisory expiry was originally enforced during CI qualification only. An otherwise valid signed artifact could be activated after its mitigation review expired. A signature authenticates historical bytes; it does not extend the validity of a time-bounded risk review. | `scripts/release_artifacts.py` binds the canonical image/Python policy fingerprint into the signed inventory and checks current expiry during promotion and current production activation. A changed policy also requires newly qualified signed evidence. An actual-date negative test rejects a January 2027 activation before image pull. Read-only historical retrieval remains possible. Local logic verified; real GitHub signatures/publication remain an explicit external gate. |
| NEW-TOOL-05 | Medium | Introduced in the new immutable-image flow; caught before release | Docker's containerd store reports a local OCI index ID where the classic image store commonly reports the image config ID. Comparing the two as a single cross-machine identity would safely refuse a valid artifact, making promotion/deployment unusable. | `scripts/release_artifacts.py` hashes the actual config blob from the qualified Docker archive, validates config and filesystem layer readback, obtains the platform config from the immutable registry manifest, and separately records the verified local store ID for startup. Actual archive save/load and two-release local registry retrieval pass; wrong config and source revision are rejected. Both store-ID shapes are unit tested. No second physical Docker engine or real GitHub signature was fabricated. |

## Evidence

- `docs/remediation/image-advisory-matrix.json`, `final-image-disposition-evidence.json`, `zlib-source-evidence.json`: exact backend config/image identity, individual advisory conditions and their limitations.
- `docs/remediation/frontend-image-audit-evidence.json`: retained old-image matrix and fresh runtime-candidate scan, with no new frontend suppressions.
- `backend/docker/build_xml_security.py`, `backend/docker/backport_tarfile_security.py`, `scripts/qa/qualify_runtime_image.py`: reproducible parser repairs and actual negative fixtures. The tar hard-link regression was part of NEW-TOOL-01's parser remediation, not a sixth issue group.
- `scripts/test_image_runtime_policy.py`, `scripts/test_image_advisory_policy.py`, `scripts/test_release_artifacts.py`, `scripts/test_release_current.py`: bounded policy/identity/expiry regression checks.
- `docs/remediation/artifact-retrieval-evidence.json`: real isolated registry predecessor/successor proof, with the Docker Desktop loopback adapter and evidence limits disclosed.

These observations do not reopen or rename the original DEP-03 exception-lifecycle finding, REL-04/DEP-04 release-evidence group, or SCALE-01 availability finding. Those retain their original separate status. No production writes, deployments, native application edits or data deletion were performed by this workstream.
