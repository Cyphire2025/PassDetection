# Dashboard frontend remediation — phase two

This records dashboard work and its local qualification. It does not claim a production deployment, physical camera validation, or native application changes. The original independent audit is retained separately.

## Implemented behavior

- **UI-01:** `components/ui/modal-keyboard-boundary.ts` owns modal focus entry, Tab/Shift+Tab containment, programmatic focus containment, nested-dialog precedence, Escape handling, background `inert`, scroll locking, and focus return. Destructive confirmation dialogs prefer their safe action. Pending operations can prevent closing. The audited document workspace, upload-link, email, GC and WhatsApp dialogs use it, as do export, coordinator creation, meal-plan generation, camera/upload overlays and queue-aware sign-out. The sign-out tests retain queued records and verify that pending synchronization cannot be bypassed through Escape.
- **UI-04:** shared, route and global error boundaries submit bounded metadata to the same-origin `/api/v1/observability/frontend-errors` endpoint. The payload contains only `event_id`, `fingerprint`, release, a static route template, boundary kind and an allowlisted error kind. It deliberately excludes exception messages/stacks, dynamic IDs, URL query/hash values, user identity and document data. Local reporting is capped at ten metadata groups per page lifetime, with a three-second timeout and no retry loop. The fallback shows a support reference only after validating the server's accepted UUID, including the original UUID returned for a deduplicated event. Collector failure leaves the fallback usable. This demonstrates ingestion; external retention and human response remain outside this claim.
- **QUAL-03:** production navigation no longer uses `as never`. Literal route builders use Next's generated types. Stored/externally supplied destinations go through one allowlist validator; unsafe origins, protocol-relative paths, control characters, backslashes and unknown application routes are rejected. The route-template inventory is checked against real page files. Compile checks include expected failures for invalid route literals.
- **QUAL-04:** removed the unreachable `PASSPORT_CROP` upload state and its five orphaned implementation/contract files. The working staff crop, passport camera, visa camera and visa photo flows remain. A tested capture transition preserves the accepted blob/bundle and advances to the appropriate next page.
- **ARC-02 / QUAL-02:** the upload controller now delegates document persistence/recovery/retry/replacement, final submission, pure validation, family state, generation-based operation admission and review rendering to tested owners. The parent decreased from 1,809 lines / maximum function complexity 67 to 746 / 50. Cancellation cannot release a newer operation or publish a stale response. Family acknowledgements are retained before extraction and between final submissions; cross-reload family recovery is not claimed. See [controller evidence](upload-controller.md). Passport detail delegates navigation context, adjacent-record lookup and keyboard behavior to a dedicated hook. Group WhatsApp tracking separates mutation dialogs, table rendering and pure view calculations; its parent decreased from roughly 1,700 lines to 691. Passport detail remains substantial at 1,411 lines; this work does not claim that every large component has become simple.
- **Related authentication compatibility:** an exact `409 / REFRESH_IN_PROGRESS` response triggers one delayed retry. Existing tab locks, session epochs and single-flight coordination remain. Other failures are not retried. Tests verify the intentional pre-0109 expired-session path reaches sign-in without a loop. The dashboard will require a fresh sign-in at that migration; passwords, MFA enrollment and native sessions are not changed by this client work.
- **Literal search:** tests verify percent signs, underscores and backslashes reach the API unchanged as user input. The backend owns escaping them for literal substring matching.

## Real-browser qualification boundary

The production-image suite now includes three representative workflows for Chromium, Firefox and WebKit: TLS/MFA/session/CSRF plus feature-dialog keyboard behavior and render-error ingestion; public cover upload/reload recovery/contact-proof submission; and decoded QR capture into an encrypted offline queue followed by real server reconciliation and duplicate suppression. All nine unique cases now have passing receipts on the exact final application images: six passing matrix cases, two corrected-fixture public-upload reruns and the supported Linux WebKit scanner. This is split-run evidence, not one clean nine-test invocation. The Windows WebKit host exposes neither mediaDevices nor canvas captureStream and rejects Ed25519; its failed offline attempt is retained separately. The pinned official Linux engine passed all four capability checks and the complete scanner journey in 7.1 seconds (10.7-second runner). Two initial synthetic stream starts required diagnosis of NotAllowedError; the final harness includes explicit camera retry and source diagnostics. No crypto, decoder, queue or server result was spoofed. See [browser receipt](frontend-browser-evidence.json).

Two deliberate test substitutions are documented in the specs: the camera source supplies synthetic canvas video frames while retaining the real video element, ZXing decoder and queue; external OTP delivery is substituted with an isolated synthetic database challenge while retaining real verification, proof consumption and final upload/storage APIs. The render-error case corrupts one dashboard read response to cause a controlled render exception, then calls the real collector. All three engines pass the metadata/privacy/support-reference checks. A duplicate request returns the original event UUID, and exactly one matching structured server log is read back with the declared image release and without the injected private marker; see [reporting receipt](frontend-render-error-browser-evidence.json). Authentication/fault-injection and OTP-delivery specs explicitly block service workers so network interception is deterministic; the offline-scanner spec retains the real worker. No such fixture can run against a database other than `passdetection_ci_browser`.

This lane does not establish physical camera permission/lens behavior, iOS/Android device performance, screen-reader usability, full WCAG conformance, or a complete cold-offline PWA journey. Those limits must remain explicit when reassessing UI-02.

The final Safari correction addresses pointer activation that does not move document.activeElement to the trigger: a root client tracker remembers the initiating pointer target, while keyboard input clears stale pointer state. The focused rerun validates this and keyboard precedence. The 902-case full run preceded this correction; it is not presented as a fresh 904-case single run.

For a supported Linux-only scanner rerun from Windows, `scripts/qa/run_linux_webkit.ps1` checks the exact disposable Compose project, PostgreSQL database identity and loopback TLS binding. It requires the pinned official Playwright1.62.1-noble image already pulled, mounts source/seed read-only, uses no Docker socket, and forwards raw loopback TCP within the existing Nginx namespace so the origin remains https://localhost:58443. The temporary runner removes itself, verifies existing application container/image identities afterward, and retains capabilities/results under outputs/qualification/linux-webkit. See the [official Playwright Docker documentation](https://playwright.dev/docs/docker) for the version-matching requirement. Physical cameras, permissions and real Safari hardware remain outside this synthetic-video proof.
